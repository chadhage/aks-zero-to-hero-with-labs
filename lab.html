Participant activity guide

Lab — from source code to AKS operations

You already know how code is promoted through configured dev, test, UAT, and production environments. This lab starts with code-complete software and covers nine phases: container contract → image → registry → Kubernetes → AKS → operations. Each activity has a pre-check (baseline what you know), the steps to run, a validation gate, and a post-check (validate the result). Every phase also has a scored knowledge check — a baseline quiz before and a measured quiz after to record changes in understanding. The guide records activity and assessment scores. Switch to Instructor-led to display trainer talk tracks and demo cues.

Before starting: complete the required workshop reading. Recommended resources are listed there for deeper architectural context.
Workshop files: Foundation labs F1–F5 use this site and your own workshop-notes folder. Phases 0–8 require the instructor-provided Skybridge starter repository, including its scripts, environments, application source, and deployment templates. Confirm that repository is open in VS Code before Phase 0. Commands in this guide use a Bash-compatible VS Code terminal (Git Bash, WSL, macOS, or Linux); do not run them unchanged in PowerShell.
Required gate before Phase 0: run ./scripts/verify-prerequisites.sh from the starter-repository root. Continue only when it confirms the required source, scripts, environment profiles, Dockerfiles, Compose template, Kubernetes templates, Git, curl, Docker Engine with the Compose and Scout plugins, Azure CLI, kubectl, and kind at the supported versions. Missing starter files cannot be recreated from this guide; obtain a complete bundle from the instructor.

Phase 1 — Derive the container contract

Make the release's runtime assumptions explicit before writing a Dockerfile. 0/3
Checkpoint — define what the image carries and what the platform supplies
1.1 Inventory runtime dependencies and process behavior ~20 min
◆ Pre-check
  • What does the application need from an operating system before its main process can start?
  • Which Java, native-library, certificate, user, filesystem, and network assumptions are implicit today?
  • How should the process react to startup failure and an operating-system termination signal?
▶ Do
  1. Inspect the release manifest, launch scripts, linked libraries, and existing environment documentation.
  2. Record build-time dependencies separately from runtime dependencies for the Java gateway and C++ parser.
  3. Define the entrypoint, working directory, user, writable paths, ports, and termination behavior in CONTAINER-CONTRACT.md.
./scripts/inspect-runtime.sh gateway-java
./scripts/inspect-runtime.sh parser-cpp
ldd build/parser-cpp/skybridge-parser
The Dockerfile will be an executable implementation of this contract. Do not begin with a base image and guess backward.
✓ Validation

CONTAINER-CONTRACT.md names every build-time and runtime dependency and defines how each component starts, runs, writes files, exposes ports, and terminates.

◇ Post-check
  • Which dependencies belong in a build stage but not in the runtime image?
  • Which host assumptions must become explicit image instructions?
  • What state would be lost when the container is replaced?
1.2 Define configuration, secrets, health, and observability ~12 min
◆ Pre-check
  • Which values vary by deployment stage and therefore cannot be baked into the image?
  • What is the difference between process liveness and readiness to receive traffic?
  • What must be emitted to standard output so a platform can collect useful logs?
▶ Do
  1. Classify every setting as invariant, stage configuration, or secret; define its name, format, default policy, and missing-value behavior.
  2. Define startup, readiness, and liveness signals plus the structured fields required in logs.
  3. Add configuration, secret, health, and telemetry sections to CONTAINER-CONTRACT.md.
./scripts/inventory-config.sh
./scripts/validate-contract.sh CONTAINER-CONTRACT.md
✓ Validation

The contract accounts for every stage-specific setting and secret, defines fail-fast behavior for required values, and names machine-testable health and telemetry signals.

◇ Post-check
  • Which configuration values may safely have defaults, and which must fail startup when absent?
  • How will a platform distinguish "process exists" from "safe to route traffic"?
  • Which log fields let you connect a request, image revision, Pod, and failure?
1.3 Set resource, security, and promotion acceptance criteria ~13 min
◆ Pre-check
  • Why does a scheduler need CPU and memory expectations before placing a workload?
  • What privileges and Linux capabilities does this application actually require?
  • What evidence should permit the same image digest to advance to the next stage?
▶ Do
  1. Record initial CPU and memory requests, limits, expected concurrency, and shutdown grace period.
  2. Require a non-root user, read-only runtime where possible, minimal capabilities, and no embedded credentials.
  3. Define test, scan, health, performance, provenance, and rollback gates for promotion of one immutable digest.
✓ Validation

The completed contract is specific enough to implement as a Dockerfile, Compose service, and Kubernetes container specification without rediscovering runtime requirements.

◇ Post-check
  • Which contract fields belong to the image, and which belong to the deployment platform?
  • Which digest will verify that the image tested is the image deployed to UAT?
  • What evidence will trigger rollback rather than further tuning?

Phase 2 — Separate image from environment

Externalize stage configuration so one immutable build can move through dev, test, UAT, and production. 0/3
2.1 Inventory every setting and where it lives ~15 min
◆ Pre-check
  • What makes a value deployment configuration rather than invariant application code?
  • What is the difference between config that varies by environment and config that is the same everywhere?
  • Why should a hard-coded default in source count as configuration too?
▶ Do
  1. Grep the three components and the runbook for every tunable: ports, hostnames, DB DSN, timeouts, thread pools, credentials.
  2. Sort each into per-environment vs constant, and flag any secret.
  3. Capture the result as a config table in CONFIG.md.
git grep -nEI 'password|secret|host|port|timeout|url|dsn' -- apps legacy
✓ Validation

CONFIG.md lists every setting with a column for source-of-truth today and a column marking secrets. Nothing is "we'll remember it".

◇ Post-check
  • How many secrets are currently in plaintext on a host or in the repo?
  • Which settings differ between dev and prod, and how do you know today?
  • Which current constant is likely to vary by environment?
2.2 Run one build with multiple stage configurations ~20 min
◆ Pre-check
  • Why does reading config from environment variables decouple build from deploy?
  • What is a sensible precedence order: env var, config file, built-in default?
  • What belongs in a committed .env.example, and what must never be committed?
▶ Do
  1. Refactor each component to read every per-environment setting from an environment variable, with a safe default only where it's truly universal.
  2. Add a committed .env.example documenting each variable; keep the real .env git-ignored.
  3. Run the app from the same build with the supplied dev, test, and UAT profiles and observe only the intended configuration differences.
./scripts/show-release-manifest.sh > workshop-notes/release-before.txt
./scripts/run-release.sh --env environments/dev.env
./scripts/run-release.sh --env environments/test.env
./scripts/run-release.sh --env environments/uat.env
./scripts/show-release-manifest.sh > workshop-notes/release-after.txt
diff workshop-notes/release-before.txt workshop-notes/release-after.txt
git diff --exit-code -- apps               # no source edit
✓ Validation

One build runs under dev, test, and UAT profiles with the intended behavior in each stage. No source edit or rebuild is required to promote it.

◇ Post-check
  • Which setting was hardest to externalize, and why?
  • If a value is absent, does the app fail loudly at startup or silently use a wrong default? Which do you want?
  • Why is "config in the environment" a precondition for one image promoting across environments?
2.3 Get secrets out of source and out of the image ~15 min
◆ Pre-check
  • Why is a secret baked into an image effectively public to anyone who can pull it?
  • What is the difference between a secret at build time and at run time?
  • Name two ways to inject a secret at run time without writing it to the image layers.
▶ Do
  1. Remove every credential from source and config files; replace with an env var reference.
  2. Provide secrets at run time only (an injected env var or a mounted file), never in the build.
  3. Add a pre-commit secret scan so a credential can't slip back in.
git grep -nEI 'password=|secret=|BEGIN [A-Z ]*PRIVATE KEY' -- . \
  && echo 'Review every match above' \
  || echo 'No matching tracked content found'
Boundary note: a production platform stores these in a managed secret store and injects them at deploy time. The replatform workshop covers that configuration; here, verify the secret is not in the artifact.
✓ Validation

The secret scan reports clean, the app still runs when a secret is injected at run time, and it fails clearly when the secret is missing.

◇ Post-check
  • If someone pulls your image, can they recover any credential from its layers?
  • What is your rotation story now that secrets are injected rather than baked?
  • What would you hand the AKS team as the "secret contract" for each component?

Phase 3 — Build and operate the containers

Implement the container contract, then inspect and constrain each running component. 0/4
Checkpoint — the estate runs from images rather than a runbook
3.1 Containerize the JVM gateway with a multi-stage build ~18 min
◆ Pre-check
  • What is a multi-stage build and what problem does it solve for compiled languages?
  • Why does layer order matter for build-cache hit rate?
  • Why run as a non-root user inside the container?
▶ Do
  1. Write a multi-stage Dockerfile: a build stage that compiles the gateway, a slim runtime stage with only the JRE and the artifact.
  2. Copy dependencies before source so dependency layers cache across code changes.
  3. Set a non-root user and an explicit entrypoint that reads config from the environment.
docker build -t gateway-java:0.1.0 apps/gateway-java/
docker run --rm -p 4561:4561 \
  --add-host host.docker.internal:host-gateway \
  -e GATEWAY_PORT=4561 -e PARSER_URL=http://host.docker.internal:8080 \
  gateway-java:0.1.0
host.docker.internal addresses a parser running on the host. The explicit host-gateway mapping makes this work with Docker Engine on Linux as well as Docker Desktop. A dependency-unavailable log is expected until the parser is started in 3.2; the gateway itself must remain healthy and listening.
✓ Validation

The gateway image builds, runs as non-root, listens on :4561, and honours the same env vars from Phase 2. Editing source and rebuilding reuses the dependency layer.

◇ Post-check
  • How much smaller is the runtime image than the single-stage build?
  • Which layer rebuilt when you changed one line of code — and which stayed cached?
  • What did the container carry that the "VM" made you install by hand in 1.1?
3.2 Containerize the C/C++ parser ~16 min
◆ Pre-check
  • Why is a compiled native binary especially well-suited to a tiny runtime image?
  • What is the risk of dynamically linked libraries when you swap the runtime base?
  • What does a minimal or distroless base buy you, and what does it cost?
▶ Do
  1. Write a multi-stage Dockerfile: a build stage with the C++ toolchain, a minimal runtime stage with just the binary and its required libs.
  2. Verify the binary runs on the slim base (link errors appear here, not in the build stage).
  3. Expose the parser's HTTP port and read its config from the environment.
docker build -t parser-cpp:0.1.0 apps/parser-cpp/
docker run --name parser-local -d -p 8080:8080 parser-cpp:0.1.0
curl --fail http://localhost:8080/healthz
docker rm -f parser-local
✓ Validation

The parser image builds and responds on its health endpoint from the slim runtime base, with no missing-library errors at start.

◇ Post-check
  • What broke first when you slimmed the base, and how did you diagnose it?
  • Compare the parser and gateway images — which is smaller and why?
  • Why is the C/C++ maintainer-retirement risk a little smaller once the build is captured in a Dockerfile?
3.3 Containerize the ops-console static site ~12 min
◆ Pre-check
  • Why containerize a static site at all, when a web server could just serve the files?
  • What is the build-then-serve pattern for a front-end (build assets, serve with a tiny server)?
  • How would this container get its backend URL without a rebuild?
▶ Do
  1. Multi-stage: build the console assets, then serve them from a minimal static server image.
  2. Use the supplied startup script to render a browser-readable config.js from API_BASE before the web server starts. A static nginx image does not substitute environment variables into already-built JavaScript by itself.
  3. Run it and load the console in a browser.
docker build -t ops-console:0.1.0 apps/ops-console/
docker run --name ops-console-local -d -p 3000:80 \
  -e API_BASE=http://localhost:8080 ops-console:0.1.0
curl --fail http://localhost:3000/config.js
docker rm -f ops-console-local
✓ Validation

The console loads from the container, and pointing it at a different API_BASE needs only a new env value, not a new build.

◇ Post-check
  • Give two reasons containerizing the static site is worthwhile even though a plain web server could serve it.
  • Which parts of the front-end config are baked at build time vs injected at run time, and why?
  • All three components now share one interface — what is it?
3.4 Harden, inspect, and constrain the running containers ~14 min
◆ Pre-check
  • What kinds of files should a .dockerignore keep out of the build context, and why?
  • What does an image vulnerability scan inspect?
  • What happens when a process exceeds a container memory limit?
▶ Do
  1. Add a .dockerignore to each component so build context excludes VCS, local env, and build junk.
  2. Scan each image for known CVEs and trim obvious bloat from the runtime stages.
  3. Run the gateway under controlled CPU and memory limits; inspect its logs, process list, network, mounts, and live resource use.
docker scout cves gateway-java:0.1.0
docker run -d --name gateway-limited --cpus 1 --memory 512m \
  -e GATEWAY_PORT=4561 -e PARSER_URL=http://parser.invalid:8080 \
  gateway-java:0.1.0
docker logs gateway-limited
docker stats --no-stream gateway-limited
docker inspect gateway-limited
docker rm -f gateway-limited
✓ Validation

Each image has a .dockerignore and recorded scan result, contains no secret or VCS data, and runs under explicit CPU and memory limits while exposing useful logs and resource evidence.

◇ Post-check
  • A High CVE sits in a base image. What should you do, and what should you not do?
  • Which image had the largest attack surface, and what drove it?
  • Which signal would distinguish CPU saturation, memory pressure, and an application failure?

4.2 Observe and diagnose the composed system ~15 min
◆ Pre-check
  • Where do you look when one healthy container cannot reach another?
  • How do container logs, health state, DNS, and resource usage narrow different failure classes?

▶ Do
