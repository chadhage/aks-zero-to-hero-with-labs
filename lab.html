Participant activity guide

Lab — from a hand-deployed VM to AKS

The journey from classic servers to AKS, sliced into 10–20 minute activities across eight phases: classic → containerize → Kubernetes → AKS. Each activity has a pre-check (baseline what you know), the steps to run, a validation gate, and a post-check (validate the result). Every phase also has a scored knowledge check — a baseline quiz before and a measured quiz after to record changes in understanding. Earn points as you go, and switch to Instructor-led for trainer talk tracks and demo cues.

Before starting: complete the required workshop reading. Recommended resources are listed there for deeper architectural context.

Phase 0 — Setup & the legacy baseline

Get the tools, get the sample, and document how it ships today. 0/2
0.1 Install the container toolchain and verify it ~15 min
◆ Pre-check — baseline: Confident / Fuzzy / No idea
  • What is the difference between a container image and a running container?
  • What does a container runtime give you that a plain OS process does not?
  • Where does docker build get its instructions, and what is a build context?
▶ Do
  1. Install a container engine (Docker Desktop, Podman, or Rancher Desktop) and Git.
  2. Confirm the daemon is up and you can pull and run a trivial image.
  3. Confirm you can build a local image from a one-line Dockerfile.
docker version
docker run --rm hello-world
docker run --rm -d -p 8080:80 nginx   # open http://localhost:8080
echo 'FROM alpine' > Dockerfile.test
docker build -t aks-foundations-check:1 -f Dockerfile.test .
✓ Validation

hello-world prints its greeting, nginx serves on :8080, and aks-foundations-check:1 appears in docker images.

◇ Post-check — if not "Confident" on every line, flag it before moving on
  • You ran two containers from the same nginx image — how many images were pulled?
  • Why did --rm matter, and what would you have left behind without it?
  • What is the smallest thing that has to be true for "build once, run anywhere" to hold?
0.2 Get the sample and document the legacy deployment ~10 min
◆ Pre-check
  • Name three ways a long-lived, hand-patched host drifts from its supposed twin.
  • What is a "runbook", and why is a runbook a liability as well as an asset?
  • Why is a manually configured server difficult to reproduce?
▶ Do
  1. Clone the Skybridge sample repo (gateway-java, parser-cpp, ops-console, plus a Postgres schema).
  2. Read legacy/DEPLOY-RUNBOOK.md — the current hand-deployment procedure.
  3. In BASELINE.md, list every manual step, every place a setting lives, and every host assumption.
git clone <your-fork>/skybridge-zero-to-hero.git
cd skybridge-zero-to-hero
sed -n '1,80p' legacy/DEPLOY-RUNBOOK.md
✓ Validation

Your BASELINE.md names at least five manual steps and at least three separate places configuration currently lives (files on the box, env of a shell, a hard-coded default, etc.).

◇ Post-check
  • Which manual step creates the greatest continuity risk if its owner is unavailable?
  • If you had to stand up an identical host from scratch today, what could you not reproduce?
  • Which concern has the highest business impact — patch reliability, idle capacity, or release time?

Phase 1 — Deploy it the classic way

Deploy with the existing process, then introduce a representative configuration failure. 0/3
Checkpoint — identify the limitations of the existing deployment process
1.1 Run the app on a "VM" with systemd and a runbook ~20 min
◆ Pre-check
  • What does systemd manage, and what does it not manage?
  • When you copy a JAR onto a host and start it, what carries the runtime version — the host or the artifact?
  • Why is "it started on my box" weak evidence that it will start on the next box?
▶ Do
  1. Start a throwaway RHEL-like container to act as your "bare VM" (no Docker inside — treat it as a host).
  2. Follow legacy/DEPLOY-RUNBOOK.md: install the JVM and toolchain, copy artifacts, drop a systemd unit, start the gateway.
  3. Confirm the gateway process is up and listening on its socket port.
docker run -it --name legacy-vm -p 4561:4561 redhat/ubi9 bash
# inside the "VM": follow the runbook by hand —
# dnf install, scp-equivalent copy, write /etc/systemd/system/gateway.service,
# systemctl daemon-reload && systemctl start gateway
The point is not to master systemd — it is to notice how many hand steps stand between "source" and "running", and how none of them are written down as code.
✓ Validation

The gateway answers on :4561 from your host. Record each manual command required by the runbook.

◇ Post-check
  • How many discrete manual commands did it take? Which are the most error-prone?
  • Where did the runtime version get pinned — and could the next engineer accidentally pick a different one?
  • If this host rebooted, what would not come back automatically?
1.2 Reproduce config drift between two "identical" hosts ~12 min
◆ Pre-check
  • Define configuration drift in one sentence.
  • Why do two hosts built from "the same runbook" still end up different?
  • What class of bug only appears on one host in a pair and not the other?
▶ Do
  1. Stand up a second "VM" from the same runbook with one configuration difference (a different package version, a hand-edited timeout, or a missing environment variable).
  2. Point the same smoke test at both hosts.
  3. Record the divergent behaviour and trace it back to the config difference.
docker run -it --name legacy-vm-2 -p 4562:4561 redhat/ubi9 bash
# follow the runbook again — but change one thing, as humans do
./scripts/smoke.sh 127.0.0.1 4561   # host 1
./scripts/smoke.sh 127.0.0.1 4562   # host 2 — different result
✓ Validation

The two hosts behave differently, and you can name the exact configuration difference that caused it.

◇ Post-check
  • How long did it take to find the difference versus cause it?
  • What artifact, if it existed, would have made the two hosts provably identical?
  • Which of Skybridge's board-level pains does drift feed most directly?
1.3 Attempt a rollback the classic way ~13 min
◆ Pre-check
  • In a copy-the-binary deployment, what artifact and state do you roll back to?
  • Why is "keep the old JAR next to the new one" a fragile rollback plan?
  • What state, besides the binary, might a rollback need to also revert?
▶ Do
  1. Deploy a "bad" build of the gateway onto host 1 by following the runbook's upgrade path.
  2. Roll back to the previous build using only what the runbook and host preserved.
  3. Time it, from "we need to roll back" to "traffic is healthy again".
✓ Validation

Record the rollback duration and whether it left stale configuration, a partially applied migration, or an orphaned process.

◇ Post-check
  • What made the rollback slow or risky — the binary, the config, or the human coordination?
  • If the unit of deployment were an immutable, versioned image, how would this step change?
  • Write the one sentence you'd tell the board about today's release risk.

Phase 2 — Configuration management

Pull settings and secrets out of the box and make config a first-class, declarative thing. 0/3
2.1 Inventory every setting and where it lives ~15 min
◆ Pre-check
  • What are the three factors of the "config" factor in the twelve-factor app?
  • What is the difference between config that varies by environment and config that is the same everywhere?
  • Why should a hard-coded default in source count as configuration too?
▶ Do
  1. Grep the three components and the runbook for every tunable: ports, hostnames, DB DSN, timeouts, thread pools, credentials.
  2. Sort each into per-environment vs constant, and flag any secret.
  3. Capture the result as a config table in CONFIG.md.
grep -rniE 'password|secret|host|port|timeout|url|dsn' apps/ legacy/
✓ Validation

CONFIG.md lists every setting with a column for source-of-truth today and a column marking secrets. Nothing is "we'll remember it".

◇ Post-check
  • How many secrets are currently in plaintext on a host or in the repo?
  • Which settings differ between dev and prod, and how do you know today?
  • Which current constant is likely to vary by environment?
2.2 Externalize config to the environment (12-factor) ~20 min
◆ Pre-check
  • Why does reading config from environment variables decouple build from deploy?
  • What is a sensible precedence order: env var, config file, built-in default?
  • What belongs in a committed .env.example, and what must never be committed?
▶ Do
  1. Refactor each component to read every per-environment setting from an environment variable, with a safe default only where it's truly universal.
  2. Add a committed .env.example documenting each variable; keep the real .env git-ignored.
  3. Run the app twice from the same build with two different env files and watch behaviour change with no rebuild.
GATEWAY_PORT=4561 PARSER_URL=http://parser:8080 \
DB_DSN='postgres://app@db:5432/skybridge' ./run-gateway.sh
✓ Validation

One build, two environments, two behaviours — driven entirely by env vars. No setting requires editing source or rebuilding to change.

◇ Post-check
  • Which setting was hardest to externalize, and why?
  • If a value is absent, does the app fail loudly at startup or silently use a wrong default? Which do you want?
  • Why is "config in the environment" a precondition for one image promoting across environments?
2.3 Get secrets out of source and out of the image ~15 min
◆ Pre-check
  • Why is a secret baked into an image effectively public to anyone who can pull it?
  • What is the difference between a secret at build time and at run time?
  • Name two ways to inject a secret at run time without writing it to the image layers.
▶ Do
  1. Remove every credential from source and config files; replace with an env var reference.
  2. Provide secrets at run time only (an injected env var or a mounted file), never in the build.
  3. Add a pre-commit secret scan so a credential can't slip back in.
git ls-files | xargs grep -nE 'password=|secret=|BEGIN .*PRIVATE KEY' || echo 'clean'
Boundary note: a production platform stores these in a managed secret store and injects them at deploy time. The replatform workshop covers that configuration; here, verify the secret is not in the artifact.
✓ Validation

The secret scan reports clean, the app still runs when a secret is injected at run time, and it fails clearly when the secret is missing.

◇ Post-check
  • If someone pulls your image, can they recover any credential from its layers?
  • What is your rotation story now that secrets are injected rather than baked?
  • What would you hand the AKS team as the "secret contract" for each component?

Phase 3 — Containerize the components

One Dockerfile per component. Small, reproducible, non-root, immutable. 0/4
Checkpoint — the estate runs from images rather than a runbook
3.1 Containerize the JVM gateway with a multi-stage build ~18 min
◆ Pre-check
  • What is a multi-stage build and what problem does it solve for compiled languages?
  • Why does layer order matter for build-cache hit rate?
  • Why run as a non-root user inside the container?
▶ Do
  1. Write a multi-stage Dockerfile: a build stage that compiles the gateway, a slim runtime stage with only the JRE and the artifact.
  2. Copy dependencies before source so dependency layers cache across code changes.
  3. Set a non-root user and an explicit entrypoint that reads config from the environment.
docker build -t gateway-java:0.1.0 apps/gateway-java/
docker run --rm -p 4561:4561 \
  -e GATEWAY_PORT=4561 -e PARSER_URL=http://host.docker.internal:8080 \
  gateway-java:0.1.0
✓ Validation

The gateway image builds, runs as non-root, listens on :4561, and honours the same env vars from Phase 2. Editing source and rebuilding reuses the dependency layer.

◇ Post-check
  • How much smaller is the runtime image than the single-stage build?
  • Which layer rebuilt when you changed one line of code — and which stayed cached?
  • What did the container carry that the "VM" made you install by hand in 1.1?
3.2 Containerize the C/C++ parser ~16 min
◆ Pre-check
  • Why is a compiled native binary especially well-suited to a tiny runtime image?
  • What is the risk of dynamically linked libraries when you swap the runtime base?
  • What does a minimal or distroless base buy you, and what does it cost?
▶ Do
  1. Write a multi-stage Dockerfile: a build stage with the C++ toolchain, a minimal runtime stage with just the binary and its required libs.
  2. Verify the binary runs on the slim base (link errors appear here, not in the build stage).
  3. Expose the parser's HTTP port and read its config from the environment.
docker build -t parser-cpp:0.1.0 apps/parser-cpp/
docker run --rm -p 8080:8080 parser-cpp:0.1.0
curl -s localhost:8080/healthz
✓ Validation

The parser image builds and responds on its health endpoint from the slim runtime base, with no missing-library errors at start.

◇ Post-check
  • What broke first when you slimmed the base, and how did you diagnose it?
  • Compare the parser and gateway images — which is smaller and why?
  • Why is the C/C++ maintainer-retirement risk a little smaller once the build is captured in a Dockerfile?
3.3 Containerize the ops-console static site ~12 min
◆ Pre-check
  • Why containerize a static site at all, when a web server could just serve the files?
  • What is the build-then-serve pattern for a front-end (build assets, serve with a tiny server)?
  • How would this container get its backend URL without a rebuild?
▶ Do
  1. Multi-stage: build the console assets, then serve them from a minimal static server image.
  2. Wire the backend/API base URL from an env var injected at run time.
  3. Run it and load the console in a browser.
docker build -t ops-console:0.1.0 apps/ops-console/
docker run --rm -p 3000:80 -e API_BASE=http://localhost:8080 ops-console:0.1.0
# open http://localhost:3000
✓ Validation

The console loads from the container, and pointing it at a different API_BASE needs only a new env value, not a new build.

◇ Post-check
  • Give two reasons containerizing the static site is worthwhile even though a plain web server could serve it.
  • Which parts of the front-end config are baked at build time vs injected at run time, and why?
  • All three components now share one interface — what is it?
3.4 Harden the images: size, scan, and a .dockerignore ~14 min
◆ Pre-check
  • What kinds of files should a .dockerignore keep out of the build context, and why?
  • What does an image vulnerability scan inspect?
  • Why is a smaller image a security property, not just a speed one?
▶ Do
  1. Add a .dockerignore to each component so build context excludes VCS, local env, and build junk.
  2. Scan each image for known CVEs and note the highest severity.
  3. Trim obvious bloat (dev tooling, caches) from the runtime stages.
docker scout cves gateway-java:0.1.0   # or: trivy image gateway-java:0.1.0
docker image ls | grep -E 'gateway-java|parser-cpp|ops-console'
✓ Validation

Each image has a .dockerignore, a recorded scan result, and a runtime size you're prepared to defend. No secret and no .git directory is present in any layer.

◇ Post-check
  • A High CVE sits in a base image. What should you do, and what should you not do?
  • Which image had the largest attack surface, and what drove it?
  • Where in a pipeline should this scan run — before push, after push, or both?

Phase 4 — Compose the system & publish images

Run the whole estate locally with one command, then version and push it. 0/3
Checkpoint — one compose up starts the estate
4.1 Compose gateway + parser + Postgres locally ~20 min
◆ Pre-check
  • How do containers on the same Compose network find each other?
  • Why keep the database as a container in local dev but treat it as external in production?
  • What is a health check in Compose and why gate depends_on on it?
▶ Do
  1. Write compose.yaml with services for gateway, parser, ops-console, and a Postgres instance.
  2. Wire them by service name (e.g. PARSER_URL=http://parser:8080, DB_DSN=…@db:5432/…) using the env vars from Phase 2.
  3. Add health checks and ordered startup, then bring the whole thing up.
docker compose up -d
docker compose ps
./scripts/smoke.sh 127.0.0.1 4561    # end-to-end through the composed stack
✓ Validation

All services report healthy, and a socket message travels client → gateway → parser → Postgres and back, entirely from images.

◇ Post-check
  • Trace the message path across the composed services out loud.
  • Compare "stand this up" now vs the runbook in Phase 1 — what changed about reproducibility?
  • Why does the database being external in prod not change your app's config contract?
4.2 Tag by semver and by commit SHA ~15 min
◆ Pre-check
  • What does an image tag commit you to operationally, versus an image digest?
  • Why tag by git SHA in addition to a human-friendly semver?
  • What is a mutable tag, and what breaks when a mutable tag is retagged over a running version?
▶ Do
  1. Retag each image with both a semver (0.1.0) and the short commit SHA (sha-abc1234).
  2. Record the digest of each build.
  3. Decide, in RELEASING.md, which tag is your promotion handle and which is your provenance handle.
SHA=$(git rev-parse --short HEAD)
docker tag gateway-java:0.1.0 gateway-java:sha-$SHA
docker image inspect gateway-java:0.1.0 --format '{{index .RepoDigests 0}}'
✓ Validation

Every component carries a semver tag and a SHA tag, and you can state which tag you'd reference in a deploy and which you'd use to trace provenance.

◇ Post-check
  • Why is deploying by digest more deterministic than deploying by tag?
  • What OCI labels (commit, build id, semver) would make later A/B analysis easier?
  • How does SHA-tagging pre-answer "which commit is in prod right now?"
4.3 Push versioned images to a registry ~18 min
◆ Pre-check
  • What is a container registry, and what is a repository within it?
  • Why is "build in CI and push" preferable to "build on a laptop and push"?
  • What does immutability at the registry level protect you from?
▶ Do
  1. Log in to a registry (any OCI registry — a local one, GHCR, Docker Hub, or an Azure Container Registry).
  2. Push each image with both tags.
  3. Pull them on a clean machine (or after a local prune) to validate portability.
docker login <registry>
docker tag gateway-java:0.1.0 <registry>/gateway-java:0.1.0
docker push <registry>/gateway-java:0.1.0
docker push <registry>/gateway-java:sha-$SHA
If you're using Azure Container Registry, az acr build can build server-side and push in one step — but plain docker push to any registry is enough to satisfy this activity.
✓ Validation

All three components exist in the registry with semver and SHA tags, and you pulled at least one back successfully from a clean state.

◇ Post-check
  • How does a consumer pull by digest vs by tag, and which is more deterministic?
  • Where should CVE scanning sit relative to the push — before, after, or both?
  • If a pull fails with "not found", what are the two most likely causes?

Phase 5 — A container-based development lifecycle

Automate the build and close the inner/outer loop before you hand the images to an orchestrator. 0/3
Checkpoint — each commit produces a scanned, versioned, published image
5.1 CI: build, test, scan, and push on every commit ~20 min
◆ Pre-check
  • What are the minimum stages of a container CI pipeline?
  • Why tag the image with the commit SHA inside CI rather than a human tag?
  • What should a failing CVE gate do to a build, and what should it not do automatically?
▶ Do
  1. Add a workflow (GitHub Actions, or your CI of choice) that, on push: builds each image, runs unit tests, scans for CVEs, and pushes sha-<short> on success.
  2. Open a trivial PR that changes one line, and watch the pipeline run.
  3. Confirm the new SHA tag lands in the registry only when checks are green.
# .github/workflows/build.yml (sketch)
# on: [push]  ->  build -> test -> scan -> push sha-${{ github.sha }}
git commit -am "chore: trivial change" && git push
✓ Validation

A green pipeline run publishes a new sha-<short> image per component; a deliberately failing test or scan blocks the push.

◇ Post-check
  • Why is the SHA tag the natural handle a later deployment system would consume?
  • Where would you cache layers to cut CI time meaningfully?
  • Why does provenance still matter even when you trust the developer?
5.2 Close the inner loop: dev against the same images ~15 min
◆ Pre-check
  • What is the "inner loop" vs the "outer loop" in development?
  • Why is it valuable that your local Compose stack uses the same images CI builds?
  • What is the risk if dev and CI build images differently?
▶ Do
  1. Make a small code change to the parser, rebuild locally, and run it under Compose with a fast edit-run cycle.
  2. Confirm the identical Dockerfile drives both your local build and the CI build.
  3. Note your edit-to-running time and what dominates it (build vs restart).
✓ Validation

You changed code and ran it under Compose using the same Dockerfile as CI. Sharing the build definition reduces differences between development and CI.

◇ Post-check
  • What dominated your inner-loop time, and what one change would halve it?
  • How does using the same Dockerfile reduce differences between local and CI builds?
  • How would you keep the inner loop fast without letting it diverge from the outer loop?
5.3 Define the run contract each image needs ~15 min
◆ Pre-check
  • What does any orchestrator need to know to run a container: image ref, ports, env, health, resources — what else?
  • Why is a container's run contract independent of whether Compose or Kubernetes runs it?
  • What will replace Compose's service-name networking once a scheduler is in charge?
▶ Do
  1. Write a one-page RUN-CONTRACT.md: for each component, its image name, tags, exposed ports, required env vars, secret contract, and health endpoint.
  2. Confirm the registry holds current images and CI is green.
  3. Note which fields will map one-to-one onto an orchestrator's manifest — you're about to use them.
✓ Validation

RUN-CONTRACT.md describes how to start each component from its image with only environment inputs — everything a scheduler will ask for next.

◇ Post-check
  • Which run-contract fields will become a container spec, a Service, and a ConfigMap?
  • What does Compose give you that a single host never did — and what does it still not give you?
  • If a container crashed at 3 a.m. under Compose, who restarts it? Hold that thought for Phase 6.
Phase boundary. Containerization is complete: reproducible images, configuration from the environment, a registry, and CI. Compose proved the pieces fit — but it won't self-heal, scale, or roll out safely. That is an orchestrator's job. Next you trade Compose for Kubernetes, then let Azure run Kubernetes for you.

Phase 6 — Kubernetes: orchestrate the containers

Trade Compose for a Kubernetes scheduler on a local cluster, with reconciliation, scaling, and rolling updates. 0/4
Checkpoint — the estate runs on Kubernetes with workload reconciliation
6.1 Stand up a local cluster and meet kubectl ~15 min
◆ Pre-check
  • What are the two halves of a Kubernetes cluster — control plane vs nodes — and what does each do?
  • What is kubectl, and where does it read the cluster address and credentials from?
  • What is a "context" in a kubeconfig?
▶ Do
  1. Create a throwaway local cluster with kind (or minikube / k3d).
  2. Confirm the node is Ready and inspect your current context.
kind create cluster --name z2h
kubectl config current-context
kubectl get nodes -o wide
✓ Validation

kubectl get nodes shows at least one Ready node, and your context points at the local cluster.

◇ Post-check
  • What did kind create on your machine to run the cluster?
  • Which file did your cluster credentials get written into?
  • What is the supported client/server version-skew rule you should respect?
6.2 Translate Compose into Deployments and Services ~20 min
◆ Pre-check
  • What is the difference between a Pod, a Deployment, and a Service?
  • How do two Pods find each other without hard-coding IPs?
  • What does a Deployment give you that a bare Pod does not?
▶ Do
  1. Write a Deployment + Service for the gateway and the parser, plus a dev-grade Deployment + Service + volume for Postgres.
  2. Reference the images from your registry (from Phase 4).
  3. Apply everything, watch the Pods come up, and smoke-test through the in-cluster Service.
kubectl apply -f k8s/
kubectl get pods,svc
kubectl port-forward svc/gateway 4561:4561 &
./scripts/smoke.sh 127.0.0.1 4561
✓ Validation

All Pods are Running, and a message travels client → gateway → parser → Postgres through in-cluster Service DNS.

◇ Post-check
  • Which Service type did you use, and how would traffic reach it from outside the cluster?
  • What replaced Compose's service-name networking?
  • Why is a Deployment the right controller for the gateway and parser at this stage?
6.3 Externalize config with ConfigMaps and Secrets ~15 min
◆ Pre-check
  • How does your 12-factor config from Phase 2 map onto a ConfigMap and a Secret?
  • Why is a Kubernetes Secret not the same thing as "encrypted"?
  • Where should these values ultimately come from in production?
▶ Do
  1. Move per-environment settings into a ConfigMap and credentials into a Secret.
  2. Reference them from the Deployments via envFrom / valueFrom.
  3. Change one value and roll the Deployment — no image rebuild.
kubectl create configmap gateway-config --from-env-file=.env.example
kubectl apply -f k8s/
kubectl rollout status deploy/gateway
Boundary note: a production platform injects these from a managed secret store such as Key Vault at deploy time. The replatform workshop covers that configuration; here, verify that configuration lives outside the image.
✓ Validation

Pods read every setting from the ConfigMap/Secret, and changing a value plus rolling the Deployment takes effect with no rebuild.

◇ Post-check
  • Run base64 -d on a Secret value — what does that tell you about its protection?
  • Which settings stayed constant across environments, and which varied?
  • What would inject these from a managed secret store instead of a base64 blob?
6.4 Self-heal, scale, roll out, and roll back ~18 min
◆ Pre-check
  • What does "reconcile to desired state" mean in practice?
  • What does a rolling update do to Pods, one at a time?
  • What is the difference between a readiness probe and a liveness probe?
▶ Do
  1. Delete a parser Pod and watch the Deployment replace it.
  2. Scale the parser to 3 replicas.
  3. Roll out a new image tag, then roll the Deployment back.
kubectl delete pod -l app=parser          # watch it self-heal
kubectl scale deploy/parser --replicas=3
kubectl set image deploy/parser parser=<registry>/parser-cpp:sha-$SHA
kubectl rollout undo deploy/parser
✓ Validation

The killed Pod is replaced automatically, the replica count changes on demand, and a rollout can be undone in a single command.

◇ Post-check
  • Compare this rollback to your hand-run rollback in 1.3 — what changed about speed and confidence?
  • What did the controller do that no runbook could?
  • Why do probes have to be right before you trust a rolling update?

Phase 7 — Deploy to AKS (managed Kubernetes)

Apply the same manifests to an Azure-managed cluster. 0/4
Checkpoint — the workload is running on AKS
7.1 Provision a basic AKS cluster and connect kubectl ~20 min
◆ Pre-check
  • What does AKS operate on your behalf that you ran yourself with kind?
  • What is a node pool?
  • What does az aks get-credentials write, and where?
▶ Do
  1. Create a resource group and a small AKS cluster.
  2. Merge its credentials into your kubeconfig.
  3. Confirm the nodes are Ready and your context now points at AKS.
az group create -n rg-z2h -l eastus
az aks create -g rg-z2h -n aks-z2h --node-count 2 --generate-ssh-keys
az aks get-credentials -g rg-z2h -n aks-z2h
kubectl get nodes -o wide
Cost note: an AKS cluster bills while it runs. Note the resource group so you can az group delete -n rg-z2h when you're done (see 7.4).
✓ Validation

kubectl get nodes against AKS returns Ready nodes, and your current context is the AKS cluster.

◇ Post-check
  • Which cluster components does Azure operate?
  • What is the supported version-skew rule between your kubectl and the AKS server?
