Participant activity guide

Lab — from source code to AKS operations

You already know how code is promoted through configured dev, test, UAT, and production environments. This lab starts with code-complete software and covers nine phases: container contract → image → registry → Kubernetes → AKS → operations. Each activity has a pre-check (baseline what you know), the steps to run, a validation gate, and a post-check (validate the result). Every phase also has a scored knowledge check — a baseline quiz before and a measured quiz after to record changes in understanding. The guide records activity and assessment scores. Phase 0 — Orient from the model you know

Verify the code-complete release, then contrast configured environments with immutable-image promotion. 0/2
0.1 Verify the release and container toolchain ~15 min
◆ Pre-check — baseline: Confident / Fuzzy / No idea
  • What evidence tells you a code-complete release is ready to enter promotion?
  • Which runtime dependencies are currently supplied by the target environment?
  • What is the difference between a container image and a running container?
▶ Do
  1. Run the supplied unit and integration tests for the code-complete Skybridge release.
  2. Confirm Git and the supported container engine are installed and the daemon is available.
  3. Pull and run a known image, then build a minimal local image to verify the complete tool path.
./scripts/test-release.sh
docker version
docker run --rm hello-world
docker run --rm -d -p 8080:80 nginx   # open http://localhost:8080
echo 'FROM alpine' > Dockerfile.test
docker build -t aks-workshop-check:1 -f Dockerfile.test .
✓ Validation

The supplied release tests pass, hello-world prints its greeting, nginx serves on :8080, and aks-workshop-check:1 appears in docker images.

◇ Post-check — if not "Confident" on every line, flag it before moving on
  • Which release artifacts are code complete, and which environment assumptions remain external?
  • You ran two containers from the same nginx image — how many images were pulled?
  • What must be captured before "build once, promote many" can be true?
0.2 Contrast environment promotion with image promotion ~10 min
◆ Pre-check
  • Between dev, test, UAT, and production, what changes besides application code?
  • Which environment differences have caused a release to behave differently after promotion?
  • What would it mean to promote exactly the same runtime and dependency set?
▶ Do
  1. Review the supplied release manifest and the dev, test, UAT, and production environment profiles.
  2. In PROMOTION-BASELINE.md, classify what currently travels with the release and what each environment supplies.
  3. Write the proposed invariant: one immutable image reference plus injected environment configuration produces each stage deployment.
./scripts/show-release-manifest.sh
diff environments/dev.env environments/test.env
git rev-parse HEAD
✓ Validation

PROMOTION-BASELINE.md identifies the release artifact, runtime dependencies, configuration ownership, secret boundary, and exact values that vary by stage.

◇ Post-check
  • Which current environment responsibility should move into the image?
  • Which values must remain outside the image, and why?
  • How will an immutable image reduce uncertainty without eliminating environment-specific configuration?

Phase 1 — Derive the container contract

Make the release's runtime assumptions explicit before writing a Dockerfile. 0/3
Checkpoint — define what the image carries and what the platform supplies
1.1 Inventory runtime dependencies and process behavior ~20 min
◆ Pre-check
  • What does the application need from an operating system before its main process can start?
  • Which Java, native-library, certificate, user, filesystem, and network assumptions are implicit today?
  • How should the process react to startup failure and an operating-system termination signal?
▶ Do
  1. Inspect the release manifest, launch scripts, linked libraries, and existing environment documentation.
  2. Record build-time dependencies separately from runtime dependencies for the Java gateway and C++ parser.
  3. Define the entrypoint, working directory, user, writable paths, ports, and termination behavior in CONTAINER-CONTRACT.md.
./scripts/inspect-runtime.sh gateway-java
./scripts/inspect-runtime.sh parser-cpp
ldd build/parser-cpp/skybridge-parser
The Dockerfile will be an executable implementation of this contract. Do not begin with a base image and guess backward.
✓ Validation

CONTAINER-CONTRACT.md names every build-time and runtime dependency and defines how each component starts, runs, writes files, exposes ports, and terminates.

◇ Post-check
  • Which dependencies belong in a build stage but not in the runtime image?
  • Which host assumptions must become explicit image instructions?
  • What state would be lost when the container is replaced?
1.2 Define configuration, secrets, health, and observability ~12 min
◆ Pre-check
  • Which values vary by deployment stage and therefore cannot be baked into the image?
  • What is the difference between process liveness and readiness to receive traffic?
  • What must be emitted to standard output so a platform can collect useful logs?
▶ Do
  1. Classify every setting as invariant, stage configuration, or secret; define its name, format, default policy, and missing-value behavior.
  2. Define startup, readiness, and liveness signals plus the structured fields required in logs.
  3. Add configuration, secret, health, and telemetry sections to CONTAINER-CONTRACT.md.
./scripts/inventory-config.sh
./scripts/validate-contract.sh CONTAINER-CONTRACT.md
✓ Validation

The contract accounts for every stage-specific setting and secret, defines fail-fast behavior for required values, and names machine-testable health and telemetry signals.

◇ Post-check
  • Which configuration values may safely have defaults, and which must fail startup when absent?
  • How will a platform distinguish "process exists" from "safe to route traffic"?
  • Which log fields let you connect a request, image revision, Pod, and failure?
1.3 Set resource, security, and promotion acceptance criteria ~13 min
◆ Pre-check
  • Why does a scheduler need CPU and memory expectations before placing a workload?
  • What privileges and Linux capabilities does this application actually require?
  • What evidence should permit the same image digest to advance to the next stage?
▶ Do
  1. Record initial CPU and memory requests, limits, expected concurrency, and shutdown grace period.
  2. Require a non-root user, read-only runtime where possible, minimal capabilities, and no embedded credentials.
  3. Define test, scan, health, performance, provenance, and rollback gates for promotion of one immutable digest.
✓ Validation

The completed contract is specific enough to implement as a Dockerfile, Compose service, and Kubernetes container specification without rediscovering runtime requirements.

◇ Post-check
  • Which contract fields belong to the image, and which belong to the deployment platform?
  • Which digest will verify that the image tested is the image deployed to UAT?
  • What evidence will trigger rollback rather than further tuning?

Phase 2 — Separate image from environment

Externalize stage configuration so one immutable build can move through dev, test, UAT, and production. 0/3
2.1 Inventory every setting and where it lives ~15 min
◆ Pre-check
  • What are the three factors of the "config" factor in the twelve-factor app?
  • What is the difference between config that varies by environment and config that is the same everywhere?
  • Why should a hard-coded default in source count as configuration too?
▶ Do
  1. Grep the three components and the runbook for every tunable: ports, hostnames, DB DSN, timeouts, thread pools, credentials.
  2. Sort each into per-environment vs constant, and flag any secret.
  3. Capture the result as a config table in CONFIG.md.
grep -rniE 'password|secret|host|port|timeout|url|dsn' apps/ legacy/
✓ Validation

CONFIG.md lists every setting with a column for source-of-truth today and a column marking secrets. Nothing is "we'll remember it".

◇ Post-check
  • How many secrets are currently in plaintext on a host or in the repo?
  • Which settings differ between dev and prod, and how do you know today?
  • Which current constant is likely to vary by environment?
2.2 Run one build with multiple stage configurations ~20 min
◆ Pre-check
  • Why does reading config from environment variables decouple build from deploy?
  • What is a sensible precedence order: env var, config file, built-in default?
  • What belongs in a committed .env.example, and what must never be committed?
▶ Do
  1. Refactor each component to read every per-environment setting from an environment variable, with a safe default only where it's truly universal.
  2. Add a committed .env.example documenting each variable; keep the real .env git-ignored.
  3. Run the app from the same build with the supplied dev, test, and UAT profiles and observe only the intended configuration differences.
./scripts/run-release.sh --env environments/dev.env
./scripts/run-release.sh --env environments/test.env
./scripts/run-release.sh --env environments/uat.env
git diff --exit-code                       # no rebuild or source edit
✓ Validation

One build runs under dev, test, and UAT profiles with the intended behavior in each stage. No source edit or rebuild is required to promote it.

◇ Post-check
  • Which setting was hardest to externalize, and why?
  • If a value is absent, does the app fail loudly at startup or silently use a wrong default? Which do you want?
  • Why is "config in the environment" a precondition for one image promoting across environments?
2.3 Get secrets out of source and out of the image ~15 min
◆ Pre-check
  • Why is a secret baked into an image effectively public to anyone who can pull it?
  • What is the difference between a secret at build time and at run time?
  • Name two ways to inject a secret at run time without writing it to the image layers.
▶ Do
  1. Remove every credential from source and config files; replace with an env var reference.
  2. Provide secrets at run time only (an injected env var or a mounted file), never in the build.
  3. Add a pre-commit secret scan so a credential can't slip back in.
git ls-files | xargs grep -nE 'password=|secret=|BEGIN .*PRIVATE KEY' || echo 'clean'
Boundary note: a production platform stores these in a managed secret store and injects them at deploy time. The replatform workshop covers that configuration; here, verify the secret is not in the artifact.
✓ Validation

The secret scan reports clean, the app still runs when a secret is injected at run time, and it fails clearly when the secret is missing.

◇ Post-check
  • If someone pulls your image, can they recover any credential from its layers?
  • What is your rotation story now that secrets are injected rather than baked?
  • What would you hand the AKS team as the "secret contract" for each component?

Phase 3 — Build and operate the containers

Implement the container contract, then inspect and constrain each running component. 0/4
Checkpoint — the estate runs from images rather than a runbook
3.1 Containerize the JVM gateway with a multi-stage build ~18 min
◆ Pre-check
  • What is a multi-stage build and what problem does it solve for compiled languages?
  • Why does layer order matter for build-cache hit rate?
  • Why run as a non-root user inside the container?
▶ Do
  1. Write a multi-stage Dockerfile: a build stage that compiles the gateway, a slim runtime stage with only the JRE and the artifact.
  2. Copy dependencies before source so dependency layers cache across code changes.
  3. Set a non-root user and an explicit entrypoint that reads config from the environment.
docker build -t gateway-java:0.1.0 apps/gateway-java/
docker run --rm -p 4561:4561 \
  -e GATEWAY_PORT=4561 -e PARSER_URL=http://host.docker.internal:8080 \
  gateway-java:0.1.0
✓ Validation

The gateway image builds, runs as non-root, listens on :4561, and honours the same env vars from Phase 2. Editing source and rebuilding reuses the dependency layer.

◇ Post-check
  • How much smaller is the runtime image than the single-stage build?
  • Which layer rebuilt when you changed one line of code — and which stayed cached?
  • What did the container carry that the "VM" made you install by hand in 1.1?
3.2 Containerize the C/C++ parser ~16 min
◆ Pre-check
  • Why is a compiled native binary especially well-suited to a tiny runtime image?
  • What is the risk of dynamically linked libraries when you swap the runtime base?
  • What does a minimal or distroless base buy you, and what does it cost?
▶ Do
  1. Write a multi-stage Dockerfile: a build stage with the C++ toolchain, a minimal runtime stage with just the binary and its required libs.
  2. Verify the binary runs on the slim base (link errors appear here, not in the build stage).
  3. Expose the parser's HTTP port and read its config from the environment.
docker build -t parser-cpp:0.1.0 apps/parser-cpp/
docker run --rm -p 8080:8080 parser-cpp:0.1.0
curl -s localhost:8080/healthz
✓ Validation

The parser image builds and responds on its health endpoint from the slim runtime base, with no missing-library errors at start.

◇ Post-check
  • What broke first when you slimmed the base, and how did you diagnose it?
  • Compare the parser and gateway images — which is smaller and why?
  • Why is the C/C++ maintainer-retirement risk a little smaller once the build is captured in a Dockerfile?
3.3 Containerize the ops-console static site ~12 min
◆ Pre-check
  • Why containerize a static site at all, when a web server could just serve the files?
  • What is the build-then-serve pattern for a front-end (build assets, serve with a tiny server)?
  • How would this container get its backend URL without a rebuild?
▶ Do
  1. Multi-stage: build the console assets, then serve them from a minimal static server image.
  2. Wire the backend/API base URL from an env var injected at run time.
  3. Run it and load the console in a browser.
docker build -t ops-console:0.1.0 apps/ops-console/
docker run --rm -p 3000:80 -e API_BASE=http://localhost:8080 ops-console:0.1.0
# open http://localhost:3000
✓ Validation

The console loads from the container, and pointing it at a different API_BASE needs only a new env value, not a new build.

◇ Post-check
  • Give two reasons containerizing the static site is worthwhile even though a plain web server could serve it.
  • Which parts of the front-end config are baked at build time vs injected at run time, and why?
  • All three components now share one interface — what is it?
3.4 Harden, inspect, and constrain the running containers ~14 min
◆ Pre-check
  • What kinds of files should a .dockerignore keep out of the build context, and why?
  • What does an image vulnerability scan inspect?
  • What happens when a process exceeds a container memory limit?
▶ Do
  1. Add a .dockerignore to each component so build context excludes VCS, local env, and build junk.
  2. Scan each image for known CVEs and trim obvious bloat from the runtime stages.
  3. Run the gateway under controlled CPU and memory limits; inspect its logs, process list, network, mounts, and live resource use.
docker scout cves gateway-java:0.1.0   # or: trivy image gateway-java:0.1.0
docker run -d --name gateway-limited --cpus 1 --memory 512m gateway-java:0.1.0
docker logs gateway-limited
docker stats --no-stream gateway-limited
docker inspect gateway-limited
✓ Validation

Each image has a .dockerignore and recorded scan result, contains no secret or VCS data, and runs under explicit CPU and memory limits while exposing useful logs and resource evidence.

◇ Post-check
  • A High CVE sits in a base image. What should you do, and what should you not do?
  • Which image had the largest attack surface, and what drove it?
  • Which signal would distinguish CPU saturation, memory pressure, and an application failure?

Phase 4 — Run the system with Compose

Run, observe, and troubleshoot the complete code-complete release as cooperating containers. 0/3
Checkpoint — one compose up starts the estate
4.1 Compose gateway + parser + Postgres locally ~20 min
◆ Pre-check
  • How do containers on the same Compose network find each other?
  • Why keep the database as a container in local dev but treat it as external in production?
  • What is a health check in Compose and why gate depends_on on it?
▶ Do
  1. Write compose.yaml with services for gateway, parser, ops-console, and a Postgres instance.
  2. Wire them by service name (e.g. PARSER_URL=http://parser:8080, DB_DSN=…@db:5432/…) using the env vars from Phase 2.
  3. Add health checks and ordered startup, then bring the whole thing up.
docker compose up -d
docker compose ps
./scripts/smoke.sh 127.0.0.1 4561    # end-to-end through the composed stack
✓ Validation

All services report healthy, and a socket message travels client → gateway → parser → Postgres and back, entirely from images.

◇ Post-check
  • Trace the message path across the composed services out loud.
  • Compare "stand this up" now vs the runbook in Phase 1 — what changed about reproducibility?
  • Why does the database being external in prod not change your app's config contract?
4.2 Observe and diagnose the composed system ~15 min
◆ Pre-check
  • Where do you look when one healthy container cannot reach another?
  • How do container logs, health state, DNS, and resource usage narrow different failure classes?
  • Why should one controlled change be made between diagnostic runs?
▶ Do
  1. Generate controlled traffic and record baseline latency, throughput, CPU, memory, health, and log error counts.
  2. Inject one broken service hostname, use Compose state/log/network evidence to diagnose it, then restore the configuration.
  3. Apply a CPU or memory constraint to one component and explain the resulting runtime signal.
./scripts/load.sh --duration 60s
docker compose ps
docker compose logs --since 5m gateway parser
docker compose exec gateway getent hosts parser
docker stats --no-stream
✓ Validation

COMPOSE-BASELINE.md records measured behavior, the injected symptom, evidence used to isolate it, the corrective change, and the passing retest.

◇ Post-check
  • Which evidence showed whether the failure was image, configuration, network, or dependency related?
  • How did the constrained component affect end-to-end behavior?
  • Which measurements must be preserved for comparison on Kubernetes and AKS?
4.3 Verify the same images across stage profiles ~18 min
◆ Pre-check
  • Which Compose fields describe the application, and which describe a deployment stage?
  • Why must stage promotion change configuration but not rebuild an image?
  • How can you verify that two stages use the same image content?
▶ Do
  1. Parameterize Compose with the supplied dev, test, and UAT environment profiles.
  2. Run the end-to-end test in each profile without invoking an image build.
  3. Record each container's image ID and verify it remains unchanged across the three runs.
docker compose --env-file environments/dev.env up -d --no-build
./scripts/smoke.sh 127.0.0.1 4561
docker compose images
docker compose --env-file environments/uat.env up -d --no-build
Environment configuration changes at deployment time. The image ID must not change during promotion.
✓ Validation

Dev, test, and UAT pass with the expected stage configuration while every application container retains the same image ID.

◇ Post-check
  • Which profile values changed application behavior?
  • Which invariant would be violated if CI rebuilt for UAT?
  • What identifier should the registry provide so this proof survives beyond one local engine?

Phase 5 — Register and automate

Turn tested local images into traceable, immutable promotion artifacts an orchestrator can pull. 0/3
Checkpoint — each commit produces a scanned, versioned, published image
5.1 CI: build, test, scan, and push on every commit ~20 min
◆ Pre-check
  • What are the minimum stages of a container CI pipeline?
  • Why tag the image with the commit SHA inside CI rather than a human tag?
  • What should a failing CVE gate do to a build, and what should it not do automatically?
▶ Do
  1. Add a workflow (GitHub Actions, or your CI of choice) that, on push: builds each image, runs unit tests, scans for CVEs, and pushes sha-<short> on success.
  2. Open a trivial PR that changes one line, and watch the pipeline run.
  3. Confirm the new SHA tag lands in the registry only when checks are green.
# .github/workflows/build.yml (sketch)
# on: [push]  ->  build -> test -> scan -> push sha-${{ github.sha }}
git commit -am "chore: trivial change" && git push
✓ Validation

A green pipeline run publishes a new sha-<short> image per component; a deliberately failing test or scan blocks the push.

◇ Post-check
  • Why is the SHA tag the natural handle a later deployment system would consume?
  • Where would you cache layers to cut CI time meaningfully?
  • Why does provenance still matter even when you trust the developer?
5.2 Label, scan, attest, and publish immutable images ~15 min
◆ Pre-check
  • What does an image tag commit you to operationally, versus an image digest?
  • Which metadata connects an image to source revision, build, and dependency inventory?
  • Why must promotion consume an existing digest rather than invoke another build?
▶ Do
  1. Add OCI source/revision/version labels, tag each CI-built image by semantic version and commit SHA, and generate an SBOM.
  2. Apply the vulnerability policy, push passing images, and record the registry digest returned for each component.
  3. Pull by digest into a clean environment and run the end-to-end smoke test without rebuilding.
SHA=$(git rev-parse --short HEAD)
docker scout cves gateway-java:sha-$SHA
docker sbom gateway-java:sha-$SHA
docker push <registry>/gateway-java:sha-$SHA
docker pull <registry>/gateway-java@sha256:<digest>
✓ Validation

Every component has source and revision labels, a stored scan and SBOM, immutable registry digest, and recorded results from a clean pull and smoke test.

◇ Post-check
  • Why is deploying by digest more deterministic than deploying by tag?
  • Which evidence lets an operator map a running container back to source and dependencies?
  • What should happen when the vulnerability policy fails after an image has been built?
5.3 Bind the container contract to promotion evidence ~15 min
◆ Pre-check
  • What does any orchestrator need to know to run a container: image ref, ports, env, health, resources — what else?
  • Why is a container's run contract independent of whether Compose or Kubernetes runs it?
  • What will replace Compose's service-name networking once a scheduler is in charge?
▶ Do
  1. Update CONTAINER-CONTRACT.md with each component's registry digest, ports, required env vars, secret inputs, health endpoints, resource baseline, and shutdown behavior.
  2. Record test, scan, SBOM, provenance, and promotion-gate evidence in RELEASE-EVIDENCE.md.
  3. Map each runtime field to the Kubernetes object or container-spec field that will satisfy it next.
✓ Validation

The contract names immutable registry digests and everything a scheduler must supply; RELEASE-EVIDENCE.md records the promotion-gate results for those artifacts.

◇ Post-check
  • Which run-contract fields will become a container spec, a Service, and a ConfigMap?
  • What does Compose give you that a single host never did — and what does it still not give you?
  • If a container crashed at 3 a.m. under Compose, who restarts it? Hold that thought for Phase 6.
Phase boundary. Containerization is complete: reproducible images, configuration from the environment, operational evidence, immutable registry digests, and CI. Compose validated the components together, but it does not reconcile desired state, schedule replicas across nodes, or coordinate rolling updates. That is an orchestrator's job. Next you trade Compose for Kubernetes, then let Azure run Kubernetes for you.

Phase 6 — Kubernetes: Pods, Deployments, and Services

Express the container contract on a local cluster, then practice reconciliation, rollout, and diagnosis. 0/4
Checkpoint — the estate runs on Kubernetes with workload reconciliation
6.1 Stand up a local cluster and meet kubectl ~15 min
◆ Pre-check
  • What are the two halves of a Kubernetes cluster — control plane vs nodes — and what does each do?
  • What is kubectl, and where does it read the cluster address and credentials from?
  • What is a "context" in a kubeconfig?
▶ Do
  1. Create a throwaway local cluster with kind (or minikube / k3d).
  2. Confirm the node is Ready and inspect your current context.
kind create cluster --name z2h
kubectl config current-context
kubectl get nodes -o wide
✓ Validation

kubectl get nodes shows at least one Ready node, and your context points at the local cluster.

◇ Post-check
  • What did kind create on your machine to run the cluster?
  • Which file did your cluster credentials get written into?
  • What is the supported client/server version-skew rule you should respect?
6.2 Translate the container contract into Kubernetes workloads ~20 min
◆ Pre-check
  • What is the difference between a Pod, a Deployment, and a Service?
  • How do two Pods find each other without hard-coding IPs?
  • What does a Deployment give you that a bare Pod does not?
▶ Do
  1. Write a Deployment + Service for the gateway and parser, plus a dev-grade StatefulSet + Service + persistent volume claim for Postgres.
  2. Reference immutable registry digests and implement startup/readiness/liveness probes, CPU/memory requests and limits, graceful termination, and a non-root security context.
  3. Apply everything, watch the Pods become Ready, and smoke-test through in-cluster Service DNS.
kubectl apply -f k8s/
kubectl get pods,svc
kubectl port-forward svc/gateway 4561:4561 &
./scripts/smoke.sh 127.0.0.1 4561
✓ Validation

All Pods are Ready, run as non-root with declared resources and probes, and carry a message gateway → parser → Postgres through in-cluster Service DNS.

◇ Post-check
  • Which Service type did you use, and how would traffic reach it from outside the cluster?
  • What replaced Compose's service-name networking?
  • Why is a Deployment the right controller for the gateway and parser at this stage?
6.3 Externalize config with ConfigMaps and Secrets ~15 min
◆ Pre-check
  • How does your 12-factor config from Phase 2 map onto a ConfigMap and a Secret?
  • Why is a Kubernetes Secret not the same thing as "encrypted"?
  • Where should these values ultimately come from in production?
▶ Do
  1. Move per-environment settings into a ConfigMap and credentials into a Secret.
  2. Reference them from the Deployments via envFrom / valueFrom.
  3. Change one value and roll the Deployment — no image rebuild.
kubectl create configmap gateway-config --from-env-file=.env.example
kubectl apply -f k8s/
kubectl rollout status deploy/gateway
Boundary note: a production platform injects these from a managed secret store such as Key Vault at deploy time. The replatform workshop covers that configuration; here, verify that configuration lives outside the image.
✓ Validation

Pods read every setting from the ConfigMap/Secret, and changing a value plus rolling the Deployment takes effect with no rebuild.

◇ Post-check
  • Run base64 -d on a Secret value — what does that tell you about its protection?
  • Which settings stayed constant across environments, and which varied?
  • What would inject these from a managed secret store instead of a base64 blob?
6.4 Replace failed Pods, diagnose, scale, roll out, and roll back ~18 min
◆ Pre-check
  • What does "reconcile to desired state" mean in practice?
  • What does a rolling update do to Pods, one at a time?
  • What is the difference between a readiness probe and a liveness probe?
▶ Do
  1. Delete a parser Pod and watch the Deployment replace it, then scale the parser to 3 replicas.
  2. Inject a broken image reference or readiness path and diagnose it using workload state, events, description, logs, and metrics.
  3. Restore the immutable digest, verify readiness, then roll out a new digest and undo the rollout.
kubectl delete pod -l app=parser          # watch the Deployment replace it
kubectl scale deploy/parser --replicas=3
./scripts/inject-k8s-failure.sh bad-readiness
kubectl get pods
kubectl describe pod -l app=parser
kubectl events --for deployment/parser
kubectl logs deploy/parser --all-pods
kubectl top pod -l app=parser
./scripts/reset-k8s-failure.sh
kubectl rollout undo deploy/parser
✓ Validation

The killed Pod is replaced, the injected failure is diagnosed from recorded evidence, the replica count changes on demand, and a rollout can be restored and undone.

◇ Post-check
  • Compare this rollback to your hand-run rollback in 1.3 — what changed in the steps and elapsed time?
  • What did the controller do that no runbook could?
  • Why do probes have to be right before you trust a rolling update?

Phase 7 — Deploy the workload to AKS

Deploy the same immutable images and workload contract to an Azure-managed cluster. 0/4
Checkpoint — the workload is running on AKS
7.1 Provision a basic AKS cluster and connect kubectl ~20 min
◆ Pre-check
  • What does AKS operate on your behalf that you ran yourself with kind?
  • What is a node pool?
  • What does az aks get-credentials write, and where?
▶ Do
  1. Verify Azure sign-in, active subscription, regional quota, and required permissions; then create a resource group and training AKS cluster.
  2. Merge its credentials into your kubeconfig.
  3. Confirm the nodes are Ready and your context now points at AKS.
az account show
az group create -n rg-z2h -l eastus
az aks create -g rg-z2h -n aks-z2h --node-count 2 --generate-ssh-keys
