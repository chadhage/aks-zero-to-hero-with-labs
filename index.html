From classic servers to AKS, one honest step at a time.

Before a team can run a production platform on Kubernetes, it has to leave hand-patched VMs, snowflake config, and Friday-night releases behind. AKS Zero-to-Hero takes the Skybridge messaging estate — a Java socket gateway, a C/C++ parser, and PostgreSQL — and walks it the whole way: classic → containers → Kubernetes → AKS. You finish with the workload running live on a managed AKS cluster. The production replatform workshop then takes that naive deployment and hardens it.

The brief

The same estate, one chapter earlier

Skybridge Messaging Services runs a real-time bus over persistent TCP sockets. In the main workshop it runs in production on AKS. Here, we meet it where most real systems actually are: running on RHEL VMs, scaled vertically, patched in place, released by hand — and we carry it, step by honest step, onto a live AKS cluster.

The lift

Four habits change on this journey

Zero-to-Hero is not really about Docker or kubectl syntax. It is about replacing four legacy habits — in deployment, configuration, the development lifecycle, and operations — with their cloud-native equivalents, ending on a cluster Azure runs for you.

Before Deployment

  • Artifacts copied onto a long-lived host with scp and a runbook
  • The host is a pet: patched in place, drifting from its twin
  • "Works on my machine" — because the machine is unique
  • Rollback means re-running yesterday's runbook, if you kept it

After Deployment

  • An immutable image is the unit of deployment, built once, run anywhere
  • Hosts are cattle; the image carries its own runtime
  • "Works on my machine" is the point — the machine is the image
  • Rollback is pointing at the previous image tag

Before Configuration

  • Settings hand-edited in files on each box, secrets in plaintext
  • Environments diverge silently; prod is a mystery
  • A config change is a manual, unaudited login

After Configuration

  • Config comes from the environment (12-factor), never baked into the image
  • One image promotes across dev → prod; only the environment differs
  • Secrets are injected, not committed; config is declarative and reviewable

Before Dev lifecycle

  • Build on a laptop, ship the binary, hope the deps match
  • Manual test, manual scan (if any), manual promotion
  • No provenance: which commit is in prod right now?

After Dev lifecycle

  • A pipeline builds, tests, scans, and pushes an image on every commit
  • Images are tagged by commit SHA — provenance is built in
  • The inner loop (Compose) mirrors the outer loop (registry + CI)

Before Operations

  • A handcrafted HA pair per region, failed over by hand
  • A crash at 3 a.m. waits for a human to notice and restart it
  • Scaling means a bigger VM and a maintenance window

After Operations

  • Kubernetes reconciles desired state — it self-heals and rolls out safely
  • Scaling is a replica count, not a hardware order
  • On AKS, Azure runs the control plane; you run manifests, not machines
The path

Eight phases, servers to AKS

Each phase is a short, hands-on block sliced into 15–20 minute activities. Every activity has a pre-check, steps to run, a validation gate, and a post-check — the same rhythm you'll meet in the replatform lab, so the muscle memory carries over.

0

Setup & the legacy baseline

Install the toolchain, get the Skybridge sample, and honestly document how it deploys today.

~25 min · 2 activities
1

Deploy it the classic way — and feel the pain

Stand up the app on a "VM" with systemd and a runbook. Then break it with config drift and a version skew.

~45 min · 3 activities
2

Configuration management

From hand-edited files to declarative config: externalize settings, pull secrets out of code, adopt 12-factor.

~50 min · 3 activities
3

Containerize the components

Write Dockerfiles for the gateway, parser, and console. Understand images, layers, and immutability.

~60 min · 4 activities
4

Compose the system & publish images

Run gateway + parser + Postgres together with Compose, then push versioned images to a registry.

~55 min · 3 activities
5

A container-based development lifecycle

Wire a pipeline that builds, tests, scans, and pushes on every commit — then write the run contract each image needs.

~50 min · 3 activities
6

Kubernetes: orchestrate the containers

Trade Compose for a local cluster: Deployments, Services, ConfigMaps and Secrets, plus self-heal, scale, and rollback.

~68 min · 4 activities
7

Land on AKS (managed Kubernetes)

Provision AKS, push images to ACR, deploy the same manifests, expose them, and bring the workload up live.

~73 min · 4 activities
What you leave with

By the end, you can…

Explain the tax of pets

Articulate, from experience, why hand-managed hosts create patch fragility, config drift, and slow, risky releases.

Externalize all config

Take a legacy app whose config lives on the box and make it read every setting from its environment — no rebuild to reconfigure.

Write a real Dockerfile

Produce small, layer-cached, non-root images for a JVM service, a compiled C++ binary, and a static site.

Run the system locally

Bring the whole estate up with one compose up, including a database and service-to-service networking.

Version like you mean it

Tag by semantic version and by commit SHA, push to a registry, and reason about mutable vs immutable tags.

Automate the build

Stand up CI that builds, tests, scans, and publishes an image per commit — the outer loop that GitOps will later consume.

Orchestrate on Kubernetes

Turn Compose services into Deployments and Services with externalized config, and watch the cluster self-heal, scale, and roll back.

Land it on AKS

Provision a managed cluster, push images to ACR, deploy the same manifests, and serve real traffic on an AKS load balancer.

The boundary

Where Zero-to-Hero ends and the replatform begins

This prequel lands you on AKS: the same three components run live on a managed cluster, pulled from ACR, built by CI. What it deliberately does not do is make that cluster production-grade. A public, single-pool, hand-applied deployment is exactly the naive starting point the replatform workshop assumes on day one.

You've landed on AKS — and this is the door

The next workshop, Replatforming a Real-Time Messaging System to AKS, takes your working deployment and re-architects it for production: Day-0 decisions, a private zone-redundant cluster, workload identity, the Istio mesh, GitOps rings with gated promotion, autoscaling, and cross-region failover. It assumes a workload already runs on AKS. That is precisely what you just built.
